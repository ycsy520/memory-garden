# 13 — 风险修复蓝图 (RISK REMEDIATION BLUEPRINT)

> 版本: v1.0
> 更新: 2026-07-15
> 状态: 待执行
> 定位: 面向当前代码库的 P0 / P1 安全与性能风险最小修复蓝图

---

## 1. 文档目标

本文件用于承接最近一次全项目统一审计，将“安全风险问题”和“性能风险问题”收敛成一份可执行、可验收、可逐步回归的最小修复蓝图。

本轮目标不是大重构，而是按如下顺序推进：

1. 先切断真实的安全与隐私风险。
2. 再补齐数据闭环，防止统计与同步口径失真。
3. 最后压住当前最明显的性能热点，为后续结构升级留出空间。

---

## 2. 不可违背原则

1. **先止血，后优化**
   先处理真实泄露、假成功删除、脏数据回灌、跨设备数据不一致，再处理体验层优化。

2. **最小修复优先**
   不在 P0 阶段引入大范围架构迁移，不同时改动过多主链路。

3. **数据真实性优先**
   任何修复都不得引入“看起来正常但统计不诚实”的折中方案。

4. **回归必须分批**
   每个阶段都必须能独立构建、独立验证、独立回滚。

---

## 3. 风险分层

### 3.1 P0 — 必须优先清零

- 仓库中存在真实训练备份样本，构成隐私暴露风险。
- 删除账户函数使用高权限删除，但缺少逐步校验与失败兜底。
- 云同步闭环不完整，跨设备存在“拉到云数据但未完整落地”的风险。
- 会话缺少稳定主键，后续云端合并和本地统计容易重复。
- 清空数据 / 导入备份 / 注销账户时不会清理离线同步队列，存在回灌污染。
- 首包过大，当前已经出现 `chunk > 500kB` 警告。
- `GameScreen` 是明显渲染热点，限时模式与高频状态变化会带动整页重渲。

### 3.2 P1 — 应尽快收口

- 游戏时钟模型双轨并存，暂停 / 恢复 / 限时路径复杂。
- 高频和大对象持久化仍主要依赖 `localStorage` 同步写。
- 持久化与备份缺少统一的 schema / version 协议。
- 统计派生字段存在双份真相，导入 / 拉云后易与会话列表不一致。
- 统计页存在重复计算热点，当前规模可承受，但不适合未来扩容。

---

## 4. P0 蓝图

## P0-1 移除真实备份样本

### 目标

切断仓库层面的真实用户数据暴露。

### 涉及文件

- `docs/memory-garden-backup-2026-07-15.json`
- `docs/memory-garden-backup-example.json`

### 方案

1. 删除真实备份样本。
2. 如文档需要示例，仅保留脱敏后的最小字段骨架。
3. 后续所有样例数据不得包含真实 `user_id`、时间序列、反应时或行为轨迹。

### 验收标准

- 仓库中不再保留真实训练备份样本。
- 文档中的示例数据均为脱敏 mock。

---

## P0-2 修复账户删除一致性

### 目标

避免“账户已删但业务数据残留”或“删除失败却返回成功”。

### 涉及文件

- `supabase/functions/delete-account/index.ts`

### 方案

1. 每一步删除操作都必须校验返回结果。
2. 任一步失败立即中止并返回错误。
3. 仅在业务数据清理完成后执行 `deleteUser`。
4. 为删除结果补一份最小审计日志结构。

### 验收标准

- 任一表删除失败时，接口返回失败。
- 不允许出现“部分删除成功但整体返回 success”的状态。

---

## P0-3 补齐云同步闭环

### 目标

建立“登录成功 -> 拉云 -> 落本地 -> 重建状态”的真实闭环。

### 涉及文件

- `src/services/AuthService.js`
- `src/services/SyncService.js`
- 相关 store

### 方案

1. 登录成功后统一触发 `pullFromCloud()`。
2. 将 `sessions`、叙事解锁、日记碎片、profile 真正写回本地 store。
3. 云端数据应用完成后重建统计派生字段。
4. 对首次登录和恢复登录做幂等保护，避免重复执行。

### 验收标准

- 新设备登录后，本地可完整看到云端历史、收藏、日记和统计。
- 不再存在“云端有数据，本地只落一半”的状态。

---

## P0-4 会话稳定 ID

### 目标

给统计、同步、备份和历史列表建立统一主键。

### 涉及文件

- `src/hooks/useGameEngine.js`
- `src/stores/useStatsStore.js`
- `src/services/SyncService.js`

### 方案

1. 会话在本地创建时即生成稳定 `id`。
2. 本地持久化、备份导出、云端上传统一复用同一 `id`。
3. 为旧历史数据补兼容修复路径。

### 验收标准

- 本地历史、云端回拉、备份导入不会因缺少 `id` 而重复计数。

---

## P0-5 清理离线同步队列

### 目标

切断“旧数据在重新联网后回灌云端”的污染链路。

### 涉及文件

- `src/screens/SettingsScreen.jsx`
- `src/services/SyncService.js`
- `src/services/BackupService.js`

### 方案

1. 清除数据时清理离线同步队列。
2. 导入备份时清理离线同步队列。
3. 删除账户时清理离线同步队列。
4. 视产品口径决定是否同步清理分析缓存。

### 验收标准

- 执行清空 / 导入 / 注销后重新联网，不会再上传历史脏数据。

---

## P0-6 路由懒加载

### 目标

在不改产品功能的前提下，优先压低首包体积。

### 涉及文件

- `src/App.jsx`

### 方案

1. 非首屏页面改为 `React.lazy + Suspense`。
2. 优先拆分低频页：
   - `StatsScreen`
   - `AchievementsScreen`
   - `LeaderboardScreen`
   - `GuideScreen`
   - `ModeGuideScreen`
   - `SettingsScreen`
   - `src/screens/about/*`
3. 统一轻量 fallback，避免新增突兀 loading。

### 验收标准

- 主包体积明显下降。
- 构建警告缓解，首屏只加载核心链路代码。

---

## P0-7 拆分 GameScreen 渲染热点

### 目标

降低限时模式与高频状态变化时的整页重渲。

### 涉及文件

- `src/screens/GameScreen.jsx`
- 必要时新增轻量子组件

### 方案

1. 将高频变化区域拆分为独立子组件：
   - Header
   - Progress
   - Timer HUD
   - Pause Overlay
2. 使用更细粒度 selector，避免整页跟随 `timedModeRemaining/status/progress` 重渲。
3. 对纯展示组件加 `React.memo`。

### 验收标准

- 计时变化时仅局部更新 HUD / 进度区。
- 不再因为秒级倒计时导致整页明显重绘。

---

## 5. P1 蓝图

## P1-1 统一游戏时钟模型

### 目标

逐步收敛 `rAF + legacy timeout + timed interval` 三套并存的时钟源。

### 涉及文件

- `src/hooks/useGameEngine.js`
- `src/engine/GameLoop.js`
- 相关计时组件

### 验收标准

- 所有模式共享一致的暂停 / 恢复 / 超时语义。

---

## P1-2 迁移高频持久化到 IndexedDB

### 目标

降低主线程同步写 `localStorage` 带来的卡顿与配额风险。

### 涉及文件

- `src/services/StorageService.js`
- 各 store 持久化入口
- `src/services/SyncService.js`

### 验收标准

- 高频大对象不再走 `localStorage` 同步写。
- 旧用户数据能平滑迁移。

---

## P1-3 统一 schema / version

### 目标

建立统一的状态升级协议，降低 PWA 更新后的错配风险。

### 涉及文件

- `useStatsStore.js`
- `useGardenStore.js`
- `useSettingsStore.js`
- `BackupService.js`

### 验收标准

- 各核心 store 都具备显式 schema/version 与迁移入口。

---

## P1-4 重建统计派生字段

### 目标

避免“双份真相”导致的统计口径不一致。

### 涉及文件

- `src/stores/useStatsStore.js`
- `src/services/SyncService.js`

### 验收标准

- 导入备份、拉云完成后，统计派生字段始终从 `sessions` 一致重建。

---

## P1-5 统计页性能收口

### 目标

压低 `StatsScreen` 对 `sessions` 的重复计算成本。

### 涉及文件

- `src/screens/StatsScreen.jsx`

### 验收标准

- 样本数据增大后，统计页仍保持可接受的渲染性能。

---

## 6. 推荐执行顺序

```text
第一阶段：P0-1 / P0-2 / P0-5
  先切断真实泄露、假成功删除、脏队列回灌

第二阶段：P0-3 / P0-4
  补齐同步闭环与会话主键

第三阶段：P0-6 / P0-7
  先压首包，再压游戏页重渲染热点

第四阶段：P1-1 / P1-2 / P1-3 / P1-4 / P1-5
  进入结构收口与长期治理
```

---

## 7. 成功标准

当以下条件满足时，可视为本蓝图落地成功：

1. 仓库与发布产物中不再包含真实用户备份样本。
2. 删除账户链路具备明确失败返回，不再允许假成功。
3. 跨设备登录后，云端数据可完整落地本地。
4. 清空 / 导入 / 注销后不会发生脏数据回灌。
5. 构建首包下降，非首屏页面已按路由拆包。
6. `GameScreen` 高频状态变化不再带动整页明显重渲。
